内存读取「卡 2 分钟 + 全部窗口一起卡」真实根因
修正版：排除特征码扫描（仅备注）· 依据 新_虚拟机读写.ec（DMA/PCILeech 共享通道）与调用链 · 示意
结构：N 个窗口共用唯一一条 DMA 内存通道
窗口 1
工作线程 + 掉线线程
窗口 2
工作线程 + 掉线线程
… 窗口 N
工作线程 + 掉线线程
⇅
唯一共享 DMA 通道
新_虚拟机读写.ec（PCILeech/winpmem）· 全局 VMM 句柄 · 物理串行
一个窗口「读卡」→ 全窗口连锁卡住 的完整链条
① 某个窗口读到异常状态
游戏在加载 / 掉线 / 对象未创建 / 进程重启中 → 首层指针解引用返回 0 或无效地址。
→
② 「强读强写」阻塞/重试
强读失败后内部重试、等待，同步占用 DMA 通道不放，可能持续数秒。
→
③ 其他窗口读数全部排队
其余 N-1 个窗口的 HP/坐标读取在通道/句柄上排队 → 全部停住（=你看到的「其他窗口都卡」）。
④ 滚雪球到 2 分钟：掉线线程「数据异常 → 重新定位」
读数一卡 → 掉线线程判「数据异常」（源码 20102）→ 触发重新定位 → 重新取进程/模块 + 整条指针链重读（又是大批 DMA 读）→ 通道更堵 → 更多窗口异常 → 更多重定位。全链路没有超时保护，一直拖到 2 分钟甚至更久。
三个放大因素
A. 强读=失败重试无超时
正常轮询也用强读，掉线/加载时每字段×每层×重试次数放大，且阻塞共享通道。
B. 通道无全局串行/限流
N 个窗口并发轰同一条 DMA 通道，一个卡全部排队；无全局读锁隔离。
C. CPU 满载放大
截图 CPU 已 93%；DMA 地址转换+高频轮询吃满 CPU，线程调度变慢，读更易超时。
阻塞/卡顿点 放大因素 口径：源码 20102 数据异常→重新定位；模块共享 VMM 句柄/散读ID
